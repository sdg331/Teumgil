# 틈길 · TEUMGIL

**시장을 이용하는 일상에서, 시민과 상인의 확인·협의까지.**

2026 로컬솔루션데이 · 길이음팀

틈길은 전통시장의 점포와 취급 품목을 찾고 장보기를 준비하는 경험에, 통행 불편을 알리고 처리 과정을 확인하는 경험을 연결하는 웹앱 프로젝트입니다. 시민이 남긴 의견을 운영자가 확인하고, 관련 상인의 입장과 가능한 대안을 듣고, 확인된 결과와 후속 확인을 기록하는 것을 목표로 합니다.

> **현재는 제품 설계와 개발 검증 기반을 준비한 단계입니다.** 아래 제품 기능은 구현 목표이며, 지금 실행할 수 있는 것은 문서·명세 ID·의견 초안 출력의 검증 도구입니다. 실행 가능한 앱과 배포 데모는 아직 없습니다.

## 프로젝트 소개

### 왜 틈길을 만드는가

전통시장은 상품을 판매하는 공간이면서 사람들이 함께 이동하는 생활 공간입니다. 보행과 영업 공간에서 불편이 생겼을 때, 상황을 알리는 것만으로는 위치와 사실 확인, 상인의 사정, 실행 가능한 대안과 이후의 유지 여부까지 이어가기 어렵습니다. 틈길은 이 과정을 연결하는 제품을 설계합니다.

시장지도와 장보기는 평소 시장을 이용할 이유를 만드는 기능입니다. 이용자가 점포와 재료를 살펴보다 필요한 경우 의견을 남길 수 있게 하되, 메뉴 선택이나 의견 작성을 시장 이용의 필수 조건으로 두지 않습니다.

현재 시장 전체의 문제 규모, 시민의 반복 이용, 상인의 참여 의사, 운영 주체와 현장 효과는 앞으로 검증해야 할 사항입니다. 과거 한 장소의 정비 사례나 가상 화면 시연을 시장 전체의 현재 상황과 실제 개선 성과로 일반화하지 않습니다.

### 누구를 위한 서비스인가

| 역할 | 하고 싶은 일 | 틈길이 연결하려는 과정 |
| --- | --- | --- |
| 시민·시장 고객 | 점포와 품목을 찾고, 필요한 경우 불편을 전달하고 싶습니다 | 시장 탐색·장보기 → 의견 작성 → 공개된 확인 과정과 결과 조회 |
| 상인 | 본인에게 관련된 내용을 확인하고 사정과 가능한 대안을 설명하고 싶습니다 | 필요한 범위의 의견 전달 → 입장·대안 작성 → 협의 기록 |
| 틈길 운영자 | 내용을 확인하고 당사자 협의와 이후 확인을 이어가고 싶습니다 | 위치·상황 확인 → 관련성 확인 → 협의 → 결과·후속 확인 기록 |

상인의 참여와 정보 게시, 현장 조정은 동의와 실제 조건을 전제로 합니다. 틈길 운영자는 공공기관 담당자와 다른 역할입니다.

## 기능과 이용 흐름

아래는 제품 설계 범위입니다. 화면별 동작과 예외는 [제품·화면 명세](docs/PRODUCT_SCREENS.md)에서 관리합니다.

| 기능 | 이용자가 하는 일 | 정보와 동작의 범위 |
| --- | --- | --- |
| 시장·점포 탐색 | 시장을 고르고 점포명·품목으로 검색합니다 | 평소 취급 품목의 출처·확인일을 표시합니다. 당일 재고·가격이 없으면 미확인으로 안내합니다 |
| 장보기 목록 | 재료를 직접 추가하고 체크·수정·삭제합니다 | 관련 점포를 찾는 목록입니다. 주문·결제·배송 기능으로 표현하지 않습니다 |
| 의견 작성·검토 | 위치와 상황을 적고 원문과 초안을 비교·수정합니다 | 발견 시점은 알고 있을 때 입력하고 사진은 선택합니다. 생성 방식과 미확인 정보를 구분합니다 |
| 틈길 내부 접수 | 이용자가 확인한 내용을 제출합니다 | 실제 저장 성공 후 접수 결과를 표시합니다. 초안 생성만으로 제출하지 않습니다 |
| 운영자 확인·상인 협의 | 필요한 정보를 확인하고 관련 상인에게 전달합니다 | 전달 대상·근거·범위를 구분하며, 상인 답변과 상태 변경·시민 공개를 별도로 처리합니다 |
| 결과·후속 확인 | 확인된 조치 또는 미해결 사유를 살펴봅니다 | 담당 주체·시각·사유와 후속 계획을 기록하고, 계획과 실제 수행을 구분합니다 |

시민 화면의 기본 탭은 **홈 · 시장지도 · 장바구니 · 마이**입니다. 메뉴 추천·냉장고·저장 점포·알림·POS 등은 확장 후보이며 현재 핵심 범위에 자동 포함하지 않습니다.

### 한 번의 이용은 어떻게 이어지는가

1. 시민이 시장에서 대파를 평소 취급하는 점포를 찾고 장보기 목록에 추가합니다.
2. 통행 불편을 겪었다면 시장 위치와 상황을 선택적으로 작성합니다.
3. 원문과 정리된 초안을 비교하고 필요한 부분을 수정한 뒤, 직접 제출 여부를 결정합니다.
4. 틈길 운영자가 내용을 확인하고, 관련성이 확인된 상인에게 필요한 범위만 전달합니다.
5. 상인이 입장과 가능한 대안 또는 대안이 없다는 답변을 남깁니다.
6. 운영자가 확인된 조치나 미해결 사유와 후속 확인 계획을 기록합니다.
7. 시민은 마이에서 본인에게 공개된 내용과 처리 기록을 확인합니다.

이 흐름은 같은 의견 ID와 연결된 전달·답변·이력을 사용하도록 설계했습니다. 원문·사진·내부 메모·상인 답변을 하나의 공개 본문으로 취급하지 않습니다.

### 의견 초안 AI가 맡는 일

가상 입력이 “시장 입구에 상자가 있어서 유모차가 지나가기 힘들었어요”라면, 초안은 제공된 위치와 불편을 정리하고 부족한 세부 위치·발견 시점의 확인을 도울 수 있습니다. 상자의 소유자나 위법성, 입력에 없는 날짜·주소·요청을 추측하지 않습니다.

이용자가 원문과 초안을 확인하고 제출을 결정합니다. 실제 AI 호출이 없는 시연에서는 예시 템플릿 등 실제 방식을 표시합니다. 프롬프트와 출력 규격은 준비돼 있지만 실제 모델 연동과 응답 품질 평가는 아직 수행하지 않았습니다.

### 내부 접수와 공식 신고

**틈길에 알리기**는 틈길 내부 의견 접수입니다. 공식 민원으로 자동 제출되지 않습니다. 공식 신고를 원하는 이용자는 틈길의 처리 상태나 운영자 확인과 관계없이 별도 공식 창구에서 요건을 확인하고 직접 제출합니다.

즉각적인 긴급 위험은 틈길 처리를 기다리지 않고 119·112를 이용하도록 안내합니다. 이 안내는 AI 응답 여부에 의존하지 않습니다.

### 현재 기술 구성

| 구분 | 구성 |

| 실제 인증·지도·AI 제공자 | 미선정·미연동 |

하네스에 Node.js를 사용한다는 사실이 앱 프레임워크나 백엔드 선정까지 의미하지는 않습니다.

<a id="getting-started"></a>
## 시작하기

이 절차는 **현재 저장소의 검증 도구**를 실행합니다. 프로젝트 파일이 있는 폴더에서 진행합니다.

1. Node.js 24와 npm을 준비합니다.
2. 저장소 루트의 package.json과 잠금 파일을 확인합니다.
3. 의존성을 설치하고 기본 검증을 실행합니다.

```sh
npm ci --ignore-scripts
npm run verify
```

의존성이 이미 준비돼 있고 잠금 파일 변경도 없다면 설치를 반복하지 않고 검증만 실행하면 됩니다. 최초 설치에는 패키지 다운로드가 필요하며, 기본 검증에는 API 키나 실제 AI 호출이 필요하지 않습니다.

현재 package.json에는 앱 실행·빌드 명령이 없습니다. 앱을 구성하면 실제 기술과 실행 방법을 이 절에 추가합니다.

<a id="validation"></a>
## 검증 방법

| 명령 | 목적 |
| --- | --- |
| `npm run verify` | 문서 → 명세 ID → 도구 테스트 → 가상 기준 출력 검사를 순서대로 실행 |
| `npm run check:docs` | 내부 파일 링크·코드 블록·JSON 예시와 프롬프트 안내의 출력 예시 검사 |
| `npm run check:ids` | 명세 ID의 할당·정의·참조·화면 소속·폐기 기록 검사 |
| `npm test` | 검증기·평가 CLI·문서·ID 검사기의 정상·오류 동작 검사 |
| `npm run eval:fixtures` | 사람이 작성한 가상 기준 출력 검사 |
| `npm run eval:fingerprints` | 현재 프롬프트·스키마·평가 데이터의 버전 식별 해시 확인 |

수집한 출력을 평가할 때는 [하네스의 파일 규격](docs/HARNESS.md)에 맞춘 로컬 파일을 사용합니다.

```sh
npm run eval:outputs -- .harness/predictions.json
```

이 파일은 별도로 준비해야 합니다. 실제 생성 방식을 model·template·manual 중 맞게 기록하고, 누락·중복 사례와 버전 불일치를 확인합니다.

**검사 결과는 범위에 맞게 해석합니다.** 기준 출력 통과는 실제 모델 평가가 아니며, 화면 명세의 인수 조건은 실행된 UI 테스트가 아닙니다. 앱의 접근 권한·저장·화면 사용성·실제 AI 품질·현장 효과는 각각 별도 근거로 검증합니다.

<a id="contributing"></a>
## 개발과 기여

기능 구현 외에도 화면 이해도, 문구, 오류·접근성, 운영 흐름과 평가 사례의 검토가 필요합니다.

변경을 제안할 때는 아래 내용을 포함합니다.

- 어떤 이용자의 어떤 문제를 바꾸려는지
- 관련 화면·요구사항·결정 ID와 현재 동작
- 기대 동작, 재현 방법과 가상 자료
- 데이터 공개·상태·저장 방식에 미치는 영향
- 실행한 검사와 아직 확인하지 못한 범위

기존 ID는 문서 정렬이나 이름 변경 때문에 바꾸지 않으며, 폐기 번호는 재사용하지 않습니다. 실제 이용자 원문·사진·연락처·API 키 대신 가상 자료로 이슈와 테스트를 재현합니다.

변경 후 `npm run verify`와 해당 기능에 필요한 검증을 실행합니다. 실패 사례를 삭제하거나 기준을 낮춰 성공으로 만들지 않고 원인을 확인합니다. 로컬 통과와 GitHub CI 통과는 별도로 기록합니다.
