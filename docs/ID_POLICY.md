# 명세 ID 관리

ID는 화면 위치나 정렬 순서가 아니라 **같은 요구사항·화면·검증 대상을 계속 가리키는 이름**이다. 번호와 정의 파일은 [ID 대장](spec-ids.json), 의미는 각 원본 명세에서 관리한다.

## 형식과 범위

| 형식 | 의미 | 정의 위치 |
| --- | --- | --- |
| R + 번호 | 제품 규칙 | PRODUCT_SCREENS |
| A + 번호 | 제품 인수 시나리오 | PRODUCT_SCREENS |
| D + 번호 | 결정 항목 | PLANS |
| C + 번호 | 화면 공통 규칙 | screens/COMMON |
| S + 두 자리 이상 번호 | 화면 | 해당 화면 상세의 제목, 전체 목록은 PRODUCT_SCREENS |
| Sxx-Tn | 해당 화면의 인수 조건 | 같은 화면의 상세 명세 |
| Sxx-On | 해당 화면의 세부 동작 | 같은 화면의 상세 명세 |

예: S11은 운영자 상세, S11-O1은 그 화면의 확인·추가 질문, S11-T1은 그 화면의 검증 조건이다. 화면 내 독립 번호만 적지 않고 소속 화면을 포함한다.

실제 의견·점포·전달·계정의 데이터 ID, URL, DB 키와 이 ID는 다르다. 데이터 ID의 생성·저장 방식은 D1·D7에서 정한다. 명세 번호를 데이터 레코드 키로 쓰지 않는다. 평가 사례의 별도 문자열 ID는 해당 평가 데이터가 관리한다.

## 변경 절차

1. 작업 전 대장에서 관련 ID와 정의 파일을 확인한다. 같은 대상은 기존 ID를 사용한다.
2. 새 대상은 대장의 해당 family next 값을 사용하고 다음 값으로 증가시킨다. 화면 번호는 최소 두 자리를 유지한다.
3. 원본 명세에 정의한다. 화면·공통 규칙·세부 동작은 제목, 제품 규칙·결정·인수 조건은 표 첫 열에 ID를 쓴다. 화면은 전체 화면 목록에도 같은 정의 파일로 연결한다.
4. 기존 대상을 편집·이름 변경·순서 이동해도 ID를 바꾸지 않는다. 파일만 이동하면 대장의 소유 파일과 연결을 함께 변경한다.
5. 대상을 폐기하면 active 정의 목록에서 빼고 retired에 id·reason·replaced_by를 남긴다. 대체가 없으면 빈 배열이다. 남은 참조와 화면 목록을 정리한다. 번호와 next 값을 되돌리지 않는다.
6. 분할·병합에서 의미가 달라진 새 대상에는 새 ID를 부여한다. 이전 ID를 다른 의미로 덮어쓰지 않고 대체 관계를 기록한다.
7. `npm run check:ids`와 변경에 필요한 검사를 실행한다.

대장을 현재 문서에서 매번 재생성하지 않는다. 재생성은 삭제된 ID의 이력과 할당 순서를 잃게 한다. 번호 사이 빈칸을 채우기 위해 ID를 재사용하지 않는다.

화면을 폐기할 때 소속 T·O도 폐기하거나 새 대상과 대체 관계를 남긴다. 다른 화면으로 인수 조건을 옮기면 부모 화면에 맞는 새 ID를 발급한다.

## 자동 검사

`npm run verify`에 ID 검사를 포함한다.

- 중복 등록·중복 정의, 등록되지 않은 ID와 폐기된 ID의 현재 참조
- 대장에 등록한 파일에 실제 정의가 없거나 다른 파일에 정의된 경우
- 화면 목록 누락·중복, 목록의 링크와 실제 정의 파일 불일치
- 다른 화면 아래에 들어간 T·O와 인수 조건이 없는 화면
- next와 할당 번호의 불일치, 기록 없이 사라진 중간 번호
- 같은 family로 적은 ID 범위 안의 미등록·폐기 ID

검사 범위는 루트·docs의 Markdown과 프로젝트 teumgil 스킬이다. 코드 블록의 예시, 외부 설치 자료와 실제 앱 코드·데이터 ID는 이 검사에 포함하지 않는다. 범위 표기는 두 끝에 prefix를 쓴다.

과거 작업 기록은 spec-ids:history:start와 spec-ids:history:end HTML 주석으로 감싼다. 이 영역은 새 정의로 세지 않으며, 이미 폐기된 ID를 과거 사실로 언급할 수 있다. 등록된 적 없는 ID는 이 영역에서도 오류다. 현재 명세를 이 영역에 숨기면 활성 정의 누락으로 실패한다. 주석은 실제 회고·작업 기록에만 사용한다.

검사는 현재 대장의 구조적 정합성을 확인한다. 같은 ID의 의미를 슬쩍 바꾸거나 대장과 next를 함께 고쳐 이력을 지우는 행위까지 자동으로 판별하지는 못한다. 이 부분은 변경 리뷰에서 이전 의미·대체 관계를 확인한다.
