# 화면별 레퍼런스와 구성 의도

2026-10-29 공개 자료를 직접 열고 Chromium에서 캡처한 연구 자료다. 13개 화면의 기능 계약은 [화면 명세](../PRODUCT_SCREENS.md), 시각 시작값은 [디자인 초안](../DESIGN_DRAFT.md)이 소유한다. 여기서는 **어떤 패턴을 왜 가져오는지와 틈길에 맞춘 배치**를 설명한다. 아래 배치는 구현·사용성 검증 전의 제안이다.

## 참고 자료를 보는 방법

`npm run design:board` 실행 후 `http://127.0.0.1:4175`에서 화면별 원본 캡처와 제안 배치를 나란히 본다. 캡처가 없는 새 환경에서는 `npm run design:capture`로 수집한다. Playwright Chromium이 없으면 `npx playwright install chromium`이 먼저 필요하다.

[references.json](references.json)은 화면과 출처의 연결을 관리한다. 로컬 `assets/_reference/capture-index.json`에는 실제 시각·URL·뷰포트·캡처 범위·성공 여부를 기록한다. 제3자 캡처는 Git에서 제외하며 앱 에셋으로 배포하지 않는다. 각 폴더의 LICENSE-NOTE는 재사용 허락서가 아니다.

| 출처 | 직접 확인한 것 | 적용할 범위 |
| --- | --- | --- |
| [TDS SearchField](https://tossmini-docs.toss.im/tds-mobile/components/search-field/) | 검색창 예제와 고정 시 공간 유지 설명 | 검색을 먼저 발견하게 하고 검색어·결과 맥락을 유지 |
| [TDS ListRow](https://tossmini-docs.toss.im/tds-mobile/components/ListRow/list-row-components/) | 좌측 요소·본문·우측 조작과 실제 행 예제 | 점포·재료·의견의 읽는 순서, 행과 개별 조작 분리 |
| [TDS TextField](https://tossmini-docs.toss.im/tds-mobile/components/TextField/text-field/) | label·placeholder·help와 입력 예제 | 사라지지 않는 이름표, 입력 가까이의 안내·오류 |
| [TDS BottomSheet](https://tossmini-docs.toss.im/tds-mobile/components/bottom-sheet/) | 예제 버튼을 눌러 하단 패널을 확인 | 맥락을 잃지 않는 시장·위치 선택. 긴 작성 작업은 별도 화면 |
| [TDS Result](https://tossmini-docs.toss.im/tds-mobile/components/result/) | 결과 설명·다음 행동. 캡처 기본값은 오류 화면 | 오류·접수 결과의 집중. 캡처를 접수 성공 예제로 오해하지 않음 |
| [네이버지도 공식 App Store 소개](https://apps.apple.com/kr/app/naver-map-navigation/id311867728) | 개발사가 게시한 지도·장소 목록 홍보 이미지 | 지도와 장소 정보의 관계. 실제 로그인 앱이나 현재 모든 기능을 검사한 것은 아님 |
| [GOV.UK Check answers](https://design-system.service.gov.uk/patterns/check-answers/) | 실행 예제의 항목별 검토·수정 링크 | 제출 전 정보 확인과 수정 위치 |
| [GOV.UK Confirmation](https://design-system.service.gov.uk/patterns/confirmation-pages/) | 실행 예제의 접수번호·다음 절차 | 저장 후 식별자와 다음 행동. 원본의 발송 완료 문구는 가져오지 않음 |
| [MOJ Timeline](https://design-patterns.service.justice.gov.uk/components/timeline/) | 실행 예제의 사건명·작성자·시각·상세 내용 | 처리 과정과 실제 기록. 선형 완료 단계로 해석하지 않음 |
| [Linear Triage](https://linear.app/docs/triage) | 공식 문서에 게시된 접수함 이미지 | 운영자·상인의 목록 밀도와 식별 맥락. AI 분류·우선순위 기능은 범위 밖 |

TDS는 공개 컴포넌트 문서이며 토스 앱 전체 화면의 복제품이 아니다. 네이버 자료는 홍보용 이미지여서 세부 수치 추출에 사용하지 않는다. GOV.UK·Linear의 정보 구조를 참고하되 틈길의 색·서체·문구와 한 흐름으로 통일한다. 접근이 제한된 카카오지도 페이지는 수집하지 않았다.

## 공통 진입 · 가입·로그인

TDS TextField를 참고해 이름표·도움말·오류가 유지되는 폼을 만든다. 인증이 필요한 행동에서 로그인으로 이동했다면 성공 후 안전한 앱 내부의 원래 행동으로 복귀한다. 비밀번호 표시·오류·제출 중·세션 만료를 다룬다. 실제 메일 연결이 없는 재설정·이메일 확인을 완료로 표시하지 않는다. 인증은 13개 제품 화면에 공통으로 연결하며 별도의 임의 명세 번호를 만들지 않는다.

## 13개 화면에 적용할 구성

### 홈 · [S01](../screens/DISCOVERY.md)

**TDS SearchField + ListRow.** 첫 화면의 중심은 시장 검색이다. 위쪽에 짧은 목적 문장과 검색창, 아래에 선택 시장과 장보기 이어보기를 둔다. 이용 실적·해결률·과도한 서비스 소개를 넣어 검색을 밀어내지 않는다. 목록이 없으면 직접 재료를 적는 경로를 보여 준다.

검색 결과가 바뀌어도 검색창의 위치·초점은 유지한다. 홈 복귀 시 시장·검색·스크롤 맥락을 복원한다. 읽기 실패와 정상 빈 목록을 구별한다.

### 시장지도·점포 목록 · [S02](../screens/DISCOVERY.md)

**네이버지도 소개의 지도/장소 관계 + TDS SearchField·BottomSheet.** 상단은 선택 시장과 품목 검색, 본문은 지도·목록, 선택 점포는 하단 패널로 연결한다. 모바일에서 지도 전체를 조작하지 않아도 목록만으로 점포를 찾는다. 데스크톱은 목록과 지도 또는 선택 상세를 병렬로 둘 수 있다.

점포 선택 시 같은 점포명과 ID가 목록·패널에서 이어져야 한다. 실제 지도 제공자가 없으면 목록을 주 경로로 삼고 위치 설명을 유지한다. 정교한 가상 지도를 실제 현장 지도처럼 꾸미지 않는다.

### 점포 상세 · [S03](../screens/DISCOVERY.md)

**TDS ListRow + 네이버지도 소개의 장소 정보 위계.** 점포명·위치, 평소 품목, 출처·확인일 순으로 읽게 한다. 담기 행동은 품목 가까이에 둔다. 실제 점포 사진이 없는 상황에서는 가짜 매장 사진이나 평점을 생성하지 않는다.

담은 품목은 장바구니로 이어지되 시선을 끄는 비행 효과는 쓰지 않는다. 중복·저장 실패의 피드백과 재고·가격 미확인 설명을 가까이 둔다.

### 장바구니 · [S04](../screens/SHOPPING.md)

**TDS ListRow·TextField.** 재료 입력과 체크 목록이 화면의 대부분을 차지한다. 항목의 왼쪽은 체크, 가운데는 이름, 오른쪽은 명시적 추가 조작이다. 편집·삭제와 점포 찾기를 행 전체 이동에 중첩하지 않는다.

체크 후 순서를 바꾸지 않아 손가락 아래의 다음 항목이 움직이지 않게 한다. 빈 목록·중복 재추가·다른 기기 변경·저장 실패를 [목록 정책](../screens/SHOPPING.md)에 맞춘다.

### 의견 입력 · [S05](../screens/OPINION_SUBMISSION.md)

**TDS TextField·BottomSheet.** 위치와 상황을 먼저 적고 시점·사진은 선택 영역으로 둔다. 필수 입력을 모든 선택 항목과 같은 무게로 펼치지 않는다. 위치 선택 패널을 닫아도 원문은 남는다.

실패한 사진은 해당 파일에서 재시도·제거할 수 있다. 텍스트만으로 계속할 수 있고 직접 작성 경로도 보인다. 키보드가 열린 모바일에서 대표 행동이 입력을 가리지 않아야 한다.

### 원문·초안 검토 · [S06](../screens/OPINION_SUBMISSION.md)

**GOV.UK Check answers + TDS TextField.** 생성 방식, 이용자 원문, 수정 가능한 정리 내용, 제출 행동을 구분한다. 좁은 화면에서는 세로로, 충분한 폭에서는 원문과 편집 내용을 나란히 보여 준다. 원문을 접을 경우에도 명확한 펼치기 조작을 남긴다.

AI 처리 중에는 편집 내용을 덮어쓰지 않는다. `needs_input`의 추가 확인과 접수 필수 입력을 구분하며, 실패·미설정에서도 직접 작성해 접수할 수 있다. 접수 버튼은 검토 뒤 이용자가 누른다.

### 접수 결과 · [S07](../screens/OPINION_SUBMISSION.md)

**GOV.UK Confirmation + TDS Result.** 내부 접수 사실, 실제 접수번호·시각, 내 의견 보기 순으로 집중한다. 공식 신고 안내는 아래의 독립 영역으로 둔다. 전체 화면 축하 효과나 '민원 해결' 문구는 쓰지 않는다.

응답이 끊겨 저장 여부를 모르면 재조회 경로를 보여 준다. 새로고침으로 의견을 재제출하지 않는다.

### 마이·내 의견 목록 · [S08](../screens/OPINION_OPERATIONS.md)

**TDS ListRow + Linear Triage.** 제목·장소·현재 상태·최근 시각으로 본인 기록을 찾는다. 각 행의 제목과 상태의 강약을 통일하고 통계 대시보드를 앞에 붙이지 않는다.

빈 목록·필터 결과 없음·읽기 실패·로그인 만료를 구분한다. 로그아웃하면 이전 계정의 캐시를 화면에 남기지 않는다.

### 시민 의견 상세 · [S09](../screens/OPINION_OPERATIONS.md)

**MOJ Timeline + GOV.UK Check answers.** 현재 상태와 내 제출 내용, 시민용 질문·게시, 처리 이력을 나눈다. 열린 질문이 있으면 응답 행동을 먼저 찾게 한다. 타임라인에는 실제 시민용 기록의 행동·시각·내용만 표시한다.

상인 원문이나 내부 메모를 숨김 CSS로 처리하지 않는다. API부터 제외한다. 답변 저장과 상태 변경은 다른 사건이다.

### 운영자 접수함 · [S10](../screens/OPINION_OPERATIONS.md)

**Linear Triage + TDS ListRow.** 시장·상태·의견 ID 검색과 목록에 집중한다. 데스크톱은 목록과 선택 미리보기, 모바일은 목록에서 상세 이동을 사용한다. 임의의 중요도 점수·해결률·처리 기한을 만들지 않는다.

필터 변경은 목록 영역만 갱신한다. 담당 시장이 없는 상태와 조건에 맞는 의견이 없는 상태를 구분한다.

### 운영자 처리 상세 · [S11](../screens/OPINION_OPERATIONS.md)

**Linear의 접수 맥락 + MOJ Timeline + GOV.UK 검토 구조.** 원문·첨부 맥락, 지금 수행하는 작업, 이력의 세 구역을 사용한다. 질문·전달·결과 게시를 한 거대한 폼으로 합치지 않는다. 대표 행동은 선택한 업무에 따라 하나씩 드러낸다.

전달·게시에는 대상을 표시한 미리보기를 둔다. 내부 메모와 시민용 결과의 배경·이름표를 구분한다. 동시 수정·재개·정정은 기존 기록과 사유를 확인한 뒤 수행한다.

### 상인 전달함 · [S12](../screens/OPINION_OPERATIONS.md)

**Linear Triage + TDS ListRow.** 전달된 요약·장소·시각·답변 여부를 간결하게 보여 준다. 운영자 내부 처리 상태를 상인의 수행 단계처럼 표시하지 않는다.

점포 연결 회수와 다른 전달 ID 접근을 서버에서 거부한다. 전달 없음은 협의 완료가 아니다.

### 상인 답변 · [S13](../screens/OPINION_OPERATIONS.md)

**TDS TextField + GOV.UK 검토 구조.** 받은 요약을 보며 입장, 가능한 대안 또는 대안 없음을 적는다. 저장 전에 보낼 내용을 확인하고 '운영자에게 전달'되는 범위를 명시한다.

저장 실패는 입력을 보존한다. 답변 정정은 새 기록이며, 성공 뒤 시민 공개나 내부 상태를 자동으로 바꾸지 않는다.

## 구현에서 확인할 디자인 결과

세 장면에 특히 마감을 집중한다. 품목을 담고 체크하는 장보기, 원문에서 검토를 거쳐 실제 접수번호로 이어지는 흐름, 별도 계정의 전달·답변·게시가 같은 의견에 쌓이는 흐름이다. 이 장면들의 모션은 [모션 계약](MOTION_SPEC.md)을 따른다.

최종 결과는 각 화면의 정상·빈 상태·실패를 실제 자료로 렌더링해 확인한다. 320px·390px·768px·1440px에서 위계·글자 줄바꿈·조작 영역을 보고, 키보드·200% 확대·모션 줄이기를 검사한다. 모든 화면을 같은 카드 격자로 만들거나 스크린샷만으로 저장·권한 검증을 대체하지 않는다.
