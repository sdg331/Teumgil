# 틈길 개발 하네스

MD가 안내하는 작업을 실제 파일·명령·검사 결과와 연결한다. 어떤 문서를 읽을지는 [AGENTS](../AGENTS.md), 제품 규칙은 [제품 명세](PRODUCT_SCREENS.md), 미결정 사항은 [PLANS](PLANS.md)에서 찾는다.

## 현재 실행 범위

설정은 [.node-version](../.node-version), [package.json](../package.json), [잠금 파일](../package-lock.json)을 따른다. 앱의 타입 검사·빌드·권한 테스트는 아직 없다.

```sh
npm ci --ignore-scripts
npm run verify
```

설치는 의존성이 없거나 잠금 파일에 맞춰 재설치할 때 수행한다. 일반 검증에는 API 키나 외부 AI 호출이 필요 없다.

| 명령 | 검사 대상 | 입증하지 못하는 것 |
| --- | --- | --- |
| `npm run check:docs` | 내부 파일 링크, 코드 블록, JSON 예시, 앱 AI 안내의 출력 예시 | 외부 링크·전체 Markdown 문법·앵커, 설계의 타당성 |
| `npm run check:ids` | 명세 ID 할당·정의·참조·화면 소속·목록 링크와 폐기 기록 | ID 의미의 재할당·대장 이력 삭제, 실제 데이터 ID·UI 동작 |
| `npm test` | 검증기·평가 CLI·문서 검사기의 정상·오류 동작 | 실제 앱·실제 AI 성능 |
| `npm run eval:fixtures` | 사람이 작성한 가상 기준 출력과 사례별 조건 | 실제 모델의 응답 품질 |
| `npm run eval:fingerprints` | 현재 프롬프트·스키마·평가 데이터의 SHA-256 | 어떤 모델이 호출됐는지 |
| `npm run eval:outputs -- .harness/predictions.json` | 가져온 출력의 버전·완전성·구조·사례 조건 | 의미 전체의 사실성·선언된 모델명 진위 |

기본 검증은 문서 검사 → 명세 ID 검사 → 도구 테스트 → 기준 출력 검사 순서다. 실패 단계는 0이 아닌 종료 코드를 반환한다. 실패한 검사를 통과로 보고하지 않는다. ID를 바꿀 때는 [관리 규칙](ID_POLICY.md)과 [대장](spec-ids.json)을 함께 확인한다.

## 프로젝트 스킬과 유지보수

[의견 흐름 스킬](../.agents/skills/teumgil-opinion-flow/SKILL.md)은 접수·전달·답변·상태·공개 범위를 바꿀 때, [의견 AI 평가 스킬](../.agents/skills/teumgil-opinion-eval/SKILL.md)은 앱 AI의 고정 지침·출력·평가를 바꿀 때 사용한다. 이용자 의견 한 건의 정리, 버튼 색상 변경, 발표 원고 수정은 이 개발 스킬의 적용 대상이 아니다. 두 계약을 함께 바꾸는 요청에는 필요한 스킬을 함께 사용한다.

스킬 본문이 필요한 기준 문서를 링크한다. 상세 규칙·사례·검사 코드를 스킬 옆에 복사하지 않는다. 설치된 OmD는 시각 작업을 담당하고, 틈길 스킬은 제품 흐름·앱 AI 평가를 담당한다.

`check:docs`는 프로젝트 문서와 `.agents/skills/teumgil-*` 아래 Markdown을 검사한다. 외부 스킬·역할·레퍼런스의 `.agents/` 나머지 영역과 `.codex/`, 의존성, 로컬 결과 `.harness/`는 제외한다. 새 프로젝트 스킬도 같은 접두어를 쓰면 링크 검사에 포함된다.

### 스킬을 바꾼 뒤의 확인

1. `skill-creator/scripts/quick_validate.py <스킬 폴더>`로 이름·YAML·미완성 scaffold를 확인한다. 이 스크립트는 프로젝트 의존성이 아니며 Python·PyYAML이 필요하다. 구조 검사 통과가 행동 검증은 아니다.
2. [스킬 요청 사례](../evals/skills/cases.json)를 사용한다. 각 요청에 어떤 스킬이 필요한지, 무엇을 읽고 어떤 결과를 내야 하는지와 금지 결과를 정의했다. 파일은 **기대값**이며 실행 보고서가 아니다.
3. 실제 평가를 수행할 때는 별도 임시 작업 공간의 가상 자료로 요청을 실행한다. 입력·스킬 버전·실제 선택·읽은 자료·산출물·검증 근거를 로컬에 남긴다. 예상 스킬을 미리 지정한 실행은 자동 선택 평가로 세지 않는다.
4. 명시 호출, 이름을 언급하지 않은 호출, 관련 없는 요청, 미결정 항목, 혼합 작업을 구분한다. 문서가 실제로 결정과 결과를 개선했는지 검토한다.
5. 작성자가 기대값을 보며 따라 읽은 검토는 **자체 워크스루**다. 독립 에이전트·자동 선택 평가나 성능 점수로 보고하지 않는다.

별도 에이전트 실행·호출이 필요하면 현재 허용 범위를 확인한다. 작성만 한 사례에 통과 표시를 하지 않는다. 권한·외부 전송·실제 운영의 보장은 스킬 문장이 아니라 구현과 별도 검사로 확인한다.

설계 참고: [컨텍스트 제공](https://wikidocs.net/432777), [스킬의 작업 절차](https://wikidocs.net/432779), [스킬 평가 방법](https://developers.openai.com/blog/eval-skills). 일반 조언을 늘리기보다 실제 실패와 반복 작업을 근거로 수정한다.

## 의견 초안 평가

### 고정 지침·규격·사례

- [프롬프트](prompts/opinion-draft.system.md): 제공된 진술만 정리하는 앱 AI의 고정 지침.
- [출력 스키마](prompts/opinion-draft.schema.json): JSON 구조.
- [사용 안내](prompts/README.md): 별도 사용자 입력, 출력 의미, UI·서버의 책임.
- [가상 사례](../evals/opinions/cases.json): 입력과 사람이 쓴 기대 출력, 기계 조건과 사람 검토 항목.

`missing_fields`는 추가 확인 목록이며 폼의 필수 입력이 아니다. `draft/needs_input/out_of_scope`는 생성 결과 분류이며 내부 접수·협의 상태가 아니다.

### 가져온 출력 파일

실제로 수집한 출력 전체를 아래 형태로 준비한다. 해시와 모델명은 실제 값으로 채운다. 모델이 아니라 템플릿·수동이면 출처를 각각 `template/manual`로 표시한다.

```json
{
  "metadata": {
    "source": "model",
    "provider": "실제 제공자",
    "model": "실제 모델 식별자",
    "prompt_sha256": "현재 프롬프트 해시",
    "schema_sha256": "현재 스키마 해시",
    "dataset_sha256": "현재 데이터 해시"
  },
  "results": []
}
```

위 빈 results는 형식 설명이며 평가용 완성 파일이 아니다. 모든 사례를 중복 없이 `{ "case_id": "...", "output": <반환 객체> }`로 넣는다. 빠진 사례·모르는 ID·버전 불일치는 거부한다. 기준 데이터를 실제 모델 출력으로 위장하지 않는다.

보고서는 `.harness/fixture-report.json`과 `.harness/output-report.json`으로 구분한다. 잘못된 입력은 이전 성공 결과를 `outcome: rejected`로 교체한다. 출력 파일의 출처와 모델 정보는 입력자 선언이며 API 호출 증명이 아니다.

### 결과 해석

- 구조·필드 대응·고정 안내문·지정 조건은 검증기가 확인한다.
- 원문에 없는 사실, 중립적 표현, 우회된 개인정보는 사례의 `human_review`로 사람이 검토한다.
- 프롬프트·스키마·데이터를 바꾸면 버전이 달라진다. 이전 출력을 새 버전으로 재라벨링하지 않고 다시 수집한다.
- 실제 원문·사진·키·전체 출력은 저장소나 공개 로그에 넣지 않는다. 평가에는 가상 자료를 사용한다.

## 앱 구현과 CI

[Verify 워크플로](../.github/workflows/verify.yml)는 Ubuntu·Windows에서 기본 검증을 실행하도록 작성돼 있다. 실제 GitHub 실행 여부는 원격 결과로 별도 확인한다.

앱을 구현하면 선택한 스택의 타입 검사·린트·빌드, 제품 명세 A1–A7, 데이터 계약의 무권한·저장 실패·공개 범위를 검증에 연결한다. 화면 사용성, 실제 모델 성능과 실제 현장 효과는 각각 다른 근거를 남긴다.
