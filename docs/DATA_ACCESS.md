# 틈길 데이터·권한·처리 계약

의견의 **연결 관계, 누가 어떤 기록을 변경하는지, 무엇을 보여 주는지**를 관리한다. 화면 행동은 [제품 명세](PRODUCT_SCREENS.md)에서 관리한다. 아래는 구현 전 설계안이며 실제 DB·인증이 구성됐다는 뜻은 아니다.

## 데이터 관계

한 의견 ID에 작성·검토·전달·답변·결과를 연결한다. 역할별로 의견을 복사해 별도 상태를 유지하지 않는다.

```text
시장 ── 점포 ── 평소 취급 품목
장보기 목록 ── 항목
의견 ── 정리된 초안
     ├─ 첨부
     ├─ 상인 전달 ── 상인 답변
     ├─ 처리 이력
     └─ 후속 확인 계획·결과
```

| 기록 | 필요한 정보 | 혼동하면 안 되는 것 |
| --- | --- | --- |
| 시장·점포 | ID, 시장 연결, 이름·위치·평소 품목, 출처·확인일, 가상 여부 | 평소 품목과 당일 재고·가격 |
| 장보기 항목 | 목록·항목 ID, 소유 주체, 재료명, 완료 여부 | 목록과 주문. 중복·유지 정책은 D2 |
| 의견 | ID, 작성 주체, 위치·상황 원문, 선택 발견 시점, 제출 시각, 현재 상태 | 발견 시점과 제출 시각 |
| 초안 | 원문과의 연결, 정리 내용, 생성 방식, 이용자 수정 내용 | AI의 `draft/needs_input/out_of_scope`와 의견 처리 상태 |
| 첨부 | 의견 연결, 파일 참조와 처리 상태 | 업로드 성공과 의견 제출. 보관은 D5 |
| 상인 전달 | 전달 ID, 의견 ID, 대상 상인, 전달용 내용·시각, 관련성 확인 근거 | 위치가 가까운 점포와 확인된 관련 상인 |
| 상인 답변 | 전달 ID, 답변 주체·시각, 입장, 대안 또는 대안 없음 | 답변 작성과 상태 변경·시민 공개 |
| 처리 이력 | 의견 ID, 행동, 변경 전후 상태(있다면), 담당 주체·시각·사유 | 현재 상태 하나와 실제 처리 과정 |
| 후속 확인 | 의견 ID, 담당 주체, 예정 시점, 실제 확인 시각·결과 | 계획과 실제 수행 |

필드 이름·식별자·시간 저장 형식은 앱 스택 선정 후 구체화한다. 원문은 초안으로 덮어쓰지 않는다. AI 출력이 접수·상태 변경 명령으로 실행되지 않게 한다.

## 행동별 계약

각 행은 별도 사용자 행동이다. 답변을 저장하면서 접수 상태까지 바꾸는 식의 암묵적 동작을 추가하지 않는다.

| 행동 | 실행 주체·전제 | 남길 결과 | 실패·거부 조건 |
| --- | --- | --- | --- |
| 의견 제출 | 작성자가 내용을 확인하고 제출 | 의견과 최초 내부 접수 이력, 제출 시각 | 입력 부족·저장 실패 시 접수 성공을 표시하지 않음 |
| 확인·추가 질문 | 담당 운영자가 해당 의견 확인 | 확인 내용 또는 필요한 질문, 담당자·시각 | 권한·대상 확인 실패. 원문과 발견 시점을 임의 수정하지 않음 |
| 상인에게 전달 | 운영자가 관련성과 전달할 범위 확인 | 상인 전달 기록 | 대상·근거·범위가 불명확하면 자동 전달하지 않음 |
| 상인 답변 | 해당 전달을 받은 상인 | 그 전달에 연결된 답변·시각 | 다른 상인의 전달 ID, 대상 없는 답변. 자동 시민 공개·상태 변경 금지 |
| 결과 기록 | 담당 운영자가 확인한 내용 또는 미확인 사유 보유 | 결과·담당자·시각·사유, 승인된 규칙에 따른 상태·이력 | 근거 없는 해결·공식 처리 완료, 저장 불일치 |
| 후속 확인 | 담당 주체와 예정·실제 수행 구분 | 계획 또는 수행 결과 | 계획만으로 완료 표시 금지 |

상태 변경과 이력 기록은 함께 성공하거나 함께 실패하도록 저장소에 맞춰 설계한다. 실제 API에서는 사용자·역할·의견·전달의 관계를 서버에서 검사한다. 데모 역할 전환은 이 검사를 대체하지 않는다.

## 열람·변경 범위

| 데이터·행동 | 작성 시민 | 관련 상인 | 담당 운영자 | 일반 공개 |
| --- | --- | --- | --- | --- |
| 공개 동의된 점포 정보 읽기 | 가능 | 가능 | 가능 | 가능 |
| 점포 정보 변경 | 제안 범위 미정 | 소속 점포 수정 요청 | 관리·승인 정책 미정 | 불가 |
| 장보기 목록 | 본인 목록 | 본인 목록 | 타인 목록 접근 없음 | 불가 |
| 의견 원문·사진 | 본인 내용 | 자동 접근 불가. 필요한 자료만 별도 전달 | 업무에 필요한 범위 | 불가 |
| 전달 내용·답변 | 시민용 공개 범위 D4 결정 전 자동 노출 금지 | 본인에게 전달된 건 | 관련 건 | 불가 |
| 내부 상태 변경 | 불가 | 답변만으로 변경하지 않음 | 상태 정책에 따름 | 불가 |
| 결과·이력 읽기 | 본인 건의 시민용 내용 | 전달받은 건의 필요한 내용 | 담당 범위 | 불가 |

원문·내부 메모·전달용 요약·시민용 결과를 구분한다. 상인에게 전체 의견 객체를 보내고 UI에서 일부만 숨기는 방식으로 전달 범위를 구현하지 않는다.

## 처리 상태의 현재 제안

이 표가 상태 이름과 의미의 기준이다. 화면·문구에는 같은 의미를 사용한다.

| 상태 | 의미 | 기록할 것 |
| --- | --- | --- |
| 틈길 접수 | 내부 의견을 받음 | 제출 시각 |
| 확인 중 | 운영자가 위치·상황 확인을 시작함 | 확인 주체·내용 |
| 추가 정보 필요 | 필요한 정보를 요청함 | 질문·시각 |
| 협의 중 | 관련 상인의 입장과 대안을 확인함 | 전달·답변 기록 |
| 공식 신고 안내 | 별도 공식 경로를 안내함 | 안내 사실. 공식 접수나 처리는 아님 |
| 확인된 조치 있음 | 조치를 확인함 | 무엇을 언제 확인했는지 |
| 확인 불가 / 대안 미확보 | 내용 또는 대안을 확인하지 못함 | 사유 |

**아직 전이표로 사용할 수 없다.** `공식 신고 안내`는 협의와 동시에 일어날 수 있어 별도 이벤트로 표현할지 검토가 필요하다(D3). 재개와 정정 권한도 미정이다. 상태를 코드로 고정하는 작업에서는 이 결정을 먼저 해결하고 표를 갱신한다. 모든 상태를 순차 진행 단계로 가정하지 않는다.

## 변경 검증

- 같은 의견과 전달을 역할별로 읽고 답변이 올바른 대상에 연결되는가?
- 시민·무관한 상인이 상태를 바꾸거나 타인의 원문·첨부를 읽는 요청을 서버가 거부하는가?
- 상태 변경 도중 저장이 실패했을 때 현재 상태와 이력이 불일치하지 않는가?
- 발견 시점을 모르는 의견과 대안 없는 답변도 기록되는가?
- 시민용 조회에 내부 메모·전체 상인 답변이 새어 나오지 않는가?
- 초안 생성이나 공식 경로 선택만으로 내부 처리 상태가 바뀌지 않는가?

실제 보관·정정·삭제·첨부 다운로드 정책은 D5·D7을 먼저 정한다. 제품 규칙은 [R1–R8](PRODUCT_SCREENS.md), 미결정 항목과 결정 시점은 [PLANS](PLANS.md), 저장 방법의 비교는 [ARCHITECTURE](ARCHITECTURE.md)를 읽는다.
