# 틈길 결정과 진행 기록

제품 기준은 [PRODUCT_SCREENS](PRODUCT_SCREENS.md), 데이터·상태는 [DATA_ACCESS](DATA_ACCESS.md)에 둔다. 여기에는 **선택이 필요한 것과 실제 진행 근거**만 기록한다. 제안과 채택된 결정을 구분하며, 사용자 요청 없이 아래 단계 전체를 시작하지 않는다.

## 현재 채택된 개발 기반

| 항목 | 결정 근거 | 기준 파일 |
| --- | --- | --- |
| 하네스 런타임 | 기존 환경에서 로컬 실행·CI 구성을 맞춤. 앱 스택 결정과 별개 | [.node-version](../.node-version), [package.json](../package.json), [잠금 파일](../package-lock.json) |
| 의견 출력 검증 | Ajv 기반 스키마 검사와 업무 규칙 검사 | [검증기](../scripts/lib/opinions.mjs) |
| 모델 없이 실행하는 평가 | 사람이 작성한 기준 출력과 가져온 출력 검사를 구분 | [하네스](HARNESS.md), [의견 사례](../evals/opinions/cases.json) |
| 로컬 디자인 도구 | 사용자 명령으로 OmD를 프로젝트 Codex 채널에 설치. 프로젝트 디자인 채택과는 별개 | [.agents/skills](../.agents/skills/) |

프런트·백엔드·운영 저장소, 실제 인증·지도·AI 제공자는 아직 선택되지 않았다.

## 결정이 필요한 지점

결정 주체는 사용자·제품팀이다. 에이전트는 요청 범위 안에서 대안·영향과 권고를 제시하고, 실제 채택 근거를 아래 기록에 남긴다. 설계 문서 작성을 요청한 것만으로 제품 선택을 승인받았다고 쓰지 않는다.

| ID | 결정할 질문 | 결정이 필요한 때 | 현재 제안·영향 | 결정 상태 |
| --- | --- | --- | --- | --- |
| D1 | 앱 기술과 저장은 무엇을 쓰며, 어떤 기기·세션까지 유지하는가? | 앱 초기 구성·저장 기능 구현 전 | 한 기기 가상 시연은 브라우저 저장 후보. 여러 기기·실제 운영이면 다른 접근 필요. 편집값 복구·결과 미확인 재시도의 중복 방지·동시 변경 정합성도 선택한 저장 방식에 맞춰 정함. [비교](ARCHITECTURE.md) | 미결정 |
| D2 | 장보기 중복·수량·시장별 목록 범위와 이름 수정 시 체크 상태를 어떻게 처리하는가? | 추가·수정·시장 전환 동작을 고정하기 전 | 목록·항목 데이터와 복귀·변경 동작에 영향. 검색·화면 검토는 먼저 가능 | 미결정 |
| D3 | 처리 상태·이벤트·재개·정정은 어떻게 구분하는가? | 상태 변경·이력 모델 구현 전 | 공식 신고 안내는 협의와 동시 발생 가능. [현재 상태안](DATA_ACCESS.md)을 단순 순서로 구현하면 정보가 사라짐 | 미결정 |
| D4 | 상인에게 무엇을 전달하고, 시민에게 어떤 답변·내부 기록을 보여 주는가? | 전달·조회 API와 역할별 화면 구현 전 | 관련성 판단·공개 주체·필드, 재전달과 답변 수정·재답변 정책 필요. 상인 답변 전체를 자동 공개하지 않음 | 미결정 |
| D5 | 사진·원문을 어디에 얼마나 보관하고 정정·삭제하는가? | 실제 수집·업로드 전. 데모도 파일 유지·초기화 구현 전 | 선택 사진, 개인정보 최소화, 접근·삭제·보관 방식에 영향 | 미결정 |
| D6 | 어떤 레퍼런스로 디자인을 채택하는가? | 공식 DESIGN.md 적용 전 | 현재 [디자인 초안](DESIGN_DRAFT.md)은 제안이며 시안·접근성 검증 전 | 미결정 |
| D7 | 실제 시민·상인·운영자를 어떻게 확인하고 권한을 부여하는가? | 실제 계정·운영 데이터·서버 권한 구현 전 | 데모 역할 전환은 인증이 아님. 다른 사람의 의견·첨부 접근을 서버에서 검사해야 함 | 미결정 |

관련 없는 D 항목 때문에 모든 작업을 중단하지 않는다. 예를 들어 의견 조회의 정보 구조 검토는 D1의 구현 선택 없이도 가능하다. 공개 필드를 바꾸는 작업은 D4를 해소해야 한다.

## 기록하는 방법

중요한 선택마다 날짜, 요청·근거, 채택한 값, 다른 선택을 배제한 이유, 영향받는 문서·코드, 검증과 남은 한계를 남긴다. 결정됐으면 위 D 항목을 갱신한다. 코드가 없거나 채택 전인 항목에 완료 표시를 하지 않는다.

검증 기록에는 실행 명령과 결과를 남긴다. 문서 링크 검사·기준 출력 검사·실제 모델 출력·앱 동작·현장 결과를 한 점수로 합치지 않는다.
