# 틈길 구현 구조와 기술 선택

Next.js·TypeScript의 시민·운영자·상인 화면과 서비스 API를 구현했다. 서버 저장은 PostgreSQL이며 간단한 로컬 개발·기본 테스트에는 서버 PGlite도 지원한다. 현재 선택과 보류 항목은 [결정 기록](PLANS.md)의 D1·D5·D7, 실행과 실제 API는 [개발 안내](DEVELOPMENT.md), 검증 근거는 [인수 기록](MVP_VERIFICATION.md)에서 확인한다.

## 채택한 첫 구현

사용자가 여러 기기에서 사용할 서비스 MVP와 기술 추천을 요청한 범위에서 Next.js App Router·TypeScript, Drizzle·PostgreSQL, Better Auth를 선택했다. 화면과 API를 한 저장소에서 구현하고 기존 Node.js 검증을 이어간다.

- `src/app/api/`는 HTTP 진입, `src/server/application.ts`는 계정 확인과 시장 조회를 담당한다.
- `src/server/domain.ts`는 장바구니·초안·의견·첨부·역할별 처리를 담당한다. 반환 필드는 시민·운영자·상인별로 명시적으로 구성한다.
- `src/components/ui.tsx`·`app/globals.css`는 공통 표현, `components/citizen`·`components/operations`는 화면별 행동, `lib/contracts.ts`는 HTTP 계약이다. 루트 레이아웃과 URL 페이지는 서버 컴포넌트로 두고 입력·세션·모션 경계에 클라이언트를 사용한다.
- `src/server/auth.ts`는 인증 라이브러리 설정, `schema.ts`와 `drizzle/`은 DB 정의와 적용 이력이다.
- 인증은 DB 세션을 매 요청 확인하고 본인 계정만 반환한다. 클라이언트가 역할을 지정할 수 없다.
- DB 마이그레이션과 가상 seed는 명령으로 분리한다. 서버 요청 중 스키마 생성이나 가상 자료 자동 삽입을 하지 않는다.
- 로컬 PGlite는 서버 파일 DB다. production에서는 공유 PostgreSQL·HTTPS를 요구한다.

## MVP 저장 구현 기준

서비스 저장 방식은 PostgreSQL로 결정됐다. 계정별 장보기와 의견을 별도 브라우저·기기에서 다시 읽는 구조를 구현한다. 역할별 시연도 독립 계정을 사용한다. 브라우저 저장·메모리를 공유 저장이나 권한 통제 대신 사용하지 않는다.

장보기의 범위·중복·체크는 [S04](screens/SHOPPING.md), 의견·사진·상태·공개는 [데이터 계약](DATA_ACCESS.md)의 2026-10-29 승인 정책을 따른다. 저장 결과 미확인·동시 수정·중복 요청·작성 복구의 구체 구현을 검증한다. 실제 자료 수집·보관 기간·삭제·동의와 production 배포는 별도다.

## 책임과 데이터 흐름

```text
시민 화면 ─ 운영자 화면 ─ 상인 화면
             │ 사용자 행동
             ▼
점포 검색 · 장보기 · 의견 제출 · 전달/답변 · 결과 기록
             │ 권한/입력/업무 규칙
             ▼
PostgreSQL · Drizzle transaction
의견 ID ─ 전달 ID ─ 답변·이력·후속 확인
```

그림의 기능은 책임 구분이며 각각 별도 서비스·폴더를 만들라는 뜻이 아니다. 작은 앱에서는 단순하게 구현하고, 실제 필요가 생길 때 나눈다.

| 책임 | 포함할 일 | 피할 결합 |
| --- | --- | --- |
| 화면 | 이름표, 입력, 현재 상태, 빈 결과·오류·다음 행동 | 화면마다 별도 의견 복사본을 저장하고 서로 다른 상태 유지 |
| 제품 동작 | 제품 명세의 인수 기준과 DATA_ACCESS의 행동 계약 적용 | 버튼 클릭만으로 권한·공개 범위까지 결정 |
| 저장 | 읽기·쓰기·실패 반환, 상태·이력 일관성, 초기화 | 저장 실패에도 성공 화면 전환 |
| 초안 생성 | 고정 지침과 원문 분리, 생성 방식 표시, 출력 검증 | 생성 응답을 제출·상태 변경으로 실행 |
| 외부 연동 | 실제 선택한 제공자만 연결, 실패·시간초과 처리 | 지도나 사진 존재만으로 재고·주소·내용 추정 |

실제 서버에서는 화면에서 전달받은 역할을 그대로 믿지 않고, 인증된 주체와 의견·점포·전달의 관계로 접근을 검사한다.

## 외부 기능을 추가할 때

| 기능 | 현재 상태 | 도입 시 필요한 판단 |
| --- | --- | --- |
| 지도 | 미선정 | 도식·목록으로 검토할지 실제 지도와 위치 권한이 필요한지 |
| AI | 프롬프트·출력 검증 도구만 있음 | 제공자·전송 범위·비용·고지·실패·실제 출력 평가 |
| 사진 | 실제 디코딩·메타데이터 제거·비공개 DB 첨부 구현 | 실제 자료의 동의·보관·삭제 정책은 별도 |
| 인증 | DB 세션·관리 명령·역할 범위·감사 구현 | 실제 이메일 확인·현장 관계 검증은 별도 |
| 공식 신고 | 별도 창구 안내 | 실제 연동 없이 틈길 내부 상태와 연결하지 않음 |

구체적인 외부 제품을 선정할 때는 그 시점의 공식 문서·조건을 확인하고 D 항목에 근거를 남긴다.

## 코드와 검증을 연결할 때

제품 기준은 [PRODUCT_SCREENS](PRODUCT_SCREENS.md), 대상별 접근과 이력은 [DATA_ACCESS](DATA_ACCESS.md)를 읽는다. 앱 파일 경로는 실제 구조에서 찾고, 아직 존재하지 않는 `src/`나 API를 이미 구현된 것처럼 문서화하지 않는다.

현재 [개발 하네스](HARNESS.md)에 타입 검사·린트와 서비스 테스트를 연결했고, 별도로 배포 빌드와 브라우저 시나리오를 검사한다. 저장은 요청 키·버전과 행 잠금으로 중복·충돌을 다루고, 상태·이력은 원자적으로 기록한다. 상세 조회는 repeatable-read 스냅샷을 사용한다. 계정별 초안 버전은 제출 뒤에도 증가해 옛 탭과 새 초안의 버전이 다시 같아지는 문제를 막는다. API·브라우저·현장 검증을 구분해 기록한다.
