# 의견 흐름 변경

한 의견의 작성·확인·전달·답변·결과가 같은 데이터에 연결되게 한다. 상인 답변, 상태 변경, 시민 공개를 별도 행동으로 판단한다.

## 필요한 맥락

- 화면 동작과 인수 조건: [제품 명세](../../../docs/PRODUCT_SCREENS.md).
- 역할·전달·공개·상태·이력: [데이터 계약](../../../docs/DATA_ACCESS.md).
- 해당 동작을 바꾸는 결정이 비어 있으면 [PLANS](../../../docs/PLANS.md)의 관련 D 항목만 확인한다.
- 저장·앱 초기 구성이 실제 작업에 필요할 때만 [아키텍처](../../../docs/ARCHITECTURE.md)를 읽는다.

## 작업

1. 요청이 설계·검토인지 구현인지 구분하고, 실제 코드와 저장 구성을 찾는다. 앱이 없다면 경로·API·권한이 구현됐다고 가정하지 않는다.
2. 변경할 행동마다 **실행 주체 → 대상 의견·전달 → 전제 → 저장 결과·이력 → 공개 대상**을 확인한다. 자료에 없는 상태 전이나 공개 필드는 확정하지 않는다.
3. 관련성이 확인되지 않은 상인 전달, 답변 전체의 자동 공개, 공식 경로 선택에 따른 내부 상태 변경을 발견하면 기준과 대조한다. 제안된 상태를 단순 순차 단계로 구현하지 않는다.
4. 구현 결과를 바꾸는 미결정 항목은 구체적인 선택지와 영향으로 질문한다. 저장 기술이 없어도 가능한 설계·검토는 계속한다. 이미 채택한 작은 구현 선택의 승인을 반복 요청하지 않는다.
5. 구현 요청이면 영향받는 입력·권한·저장·조회·이력·문구를 함께 수정한다. 설계·검토 요청이면 필요한 계약과 발견한 문제를 결과로 남기고 앱을 만들지 않는다.
6. 변경과 관련된 인수 조건을 확인하고, 저장·접근을 바꿨으면 실패·무권한 경우도 검증한다. 실제 존재하는 명령을 사용하고 [하네스](../../../docs/HARNESS.md)에 따라 기본 검증한다.

## 결과에 남길 것

- 어떤 행동의 전제·저장·공개가 바뀌었는지와 관련 기준·실제 수정 경로.
- 실행한 검증과 관찰 결과. 코드가 없으면 설계 검토라고 표시한다.
- 구현에 앞서 해결할 결정과 이유. 관련 없는 미정 항목을 모두 질문하지 않는다.

예: “상인이 답변하면 시민에게 보이게”라는 요청에서는 답변 저장과 공개 정책을 구분한다. D4에 시민 공개 범위가 없다면 이를 결정할 대상으로 제시한다. 전체 의견 객체나 내부 메모를 조회에 그대로 붙이지 않는다.
